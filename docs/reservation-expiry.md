# Reservation expiry operations

- Apply `migrations/20261108_reservation_20_minutes.sql` manually on the intended Neon branch. It changes only future reservation expiry times to 20 minutes. Existing `expires_at` values remain unchanged. The older 35-minute migration was removed and must not be run. The Reservations page reads the installed function's configured duration, so it currently shows 15 minutes until the migration is applied. A Git commit does not update Neon.
- A persistent Node.js OmniLock process runs `expire_reservations()` at startup and every 60 seconds. It uses a transaction-scoped PostgreSQL advisory lock, so concurrent app processes or scheduled requests cannot run it at the same time.
- For a serverless deployment, configure a trusted platform scheduler to send `POST /api/expire-reservations` every minute with `Authorization: Bearer <EXPIRY_API_SECRET>`. Set `EXPIRY_API_SECRET` only in server-side environment settings. Do not call this endpoint from browser code or put the secret in a `NEXT_PUBLIC_` variable. A timer in a serverless process is not a persistent scheduler.
- The existing PostgreSQL function makes the actual status and stock changes under row locks. The website countdown only displays the stored `expires_at`; it does not release stock. Refresh the Reservations page to see the latest committed status.
- Verify on an isolated Neon branch before enabling a hosted scheduler: create an unpaid hold, wait past its stored expiry, check it becomes EXPIRED and `inventory.reserved_quantity` decreases once, then run expiry again and confirm no further change. Also inspect a paid/CONFIRMED or dispatched order to confirm it remains unchanged.
